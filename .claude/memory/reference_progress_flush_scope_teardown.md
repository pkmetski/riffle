**Symptom:** audio listening position not reaching ABS on closing/pausing the readaloud player (matched book → audiobook peer) or the full audiobook player — especially when the user closes then *leaves the screen right away*.

**Root cause:** terminal progress writes were launched on `viewModelScope`, which is cancelled when the screen's ViewModel is cleared (androidx.lifecycle 2.10.0: `ViewModel.clear()` closes `viewModelScope` *before* `onCleared()` runs — proven in `ViewModel.jvm.kt`). Two failure modes:
- `AudiobookPlayerViewModel.onCleared()` → `pushProgressOnStop()` did `viewModelScope.launch{}` — **always** a no-op (scope already dead) → close position never synced.
- `EpubReaderViewModel.closeReadaloud()` / reader pause did `viewModelScope.launch { pushAudiobookFromReadingPosition(...) }` — a **race**: lost whenever the user backed out of the book before the PATCH round-trip finished.

The `ReaderSyncCoordinator` itself was correct (well-tested at `ReaderSyncCoordinatorTest` with `FakeAbs`); the bug was purely *which scope* invoked it.

**Fix (branch pkmetski/audiobook-abs-sync):** added `ProgressFlushScope` (`app/.../feature/reader/ProgressFlushScope.kt`) — a `@Singleton` wrapping an app-lifetime `@ProgressFlush CoroutineScope(SupervisorJob()+Dispatchers.IO)` provided in `AppModule` (mirrors the existing `@DownloadScope`). Routed the close/pause flushes in both ViewModels through `progressFlushScope.flush { ... }`. In-session periodic loops stay on `viewModelScope` (they *should* die with the screen).

**Tests:** `ProgressFlushScopeTest` (survives caller-scope cancellation + the buggy-pattern counter-test); `ReaderSyncCoordinatorTest` added two teardown-survival integration tests (readaloud-close → f9 clip start 90s reaches ABS; audiobook-player stop → audio-led cycle reaches ABS). The ViewModels aren't JVM-instantiable (Readium/Media3/Uri), so VM wiring is verified by compile+read, not a VM test — full device/e2e verification still pending. Relates to [[project_readaloud_audiobook_sync_gap]], [[project_audiobook_player_status]].

**Follow-up bug (same area): play-from-here readaloud → audiobook player resumed at chapter start.** Root cause: leaving the reader runs `onReaderClosed → runReaderSyncCycle`, which writes the ABS audiobook peer from the COARSE reading position (the page the reader sits on). "Play from here" only seeks the AUDIO, never moving the reader off the chapter-top page, so the reconcile clobbers the precise narrated sentence with the page top (reproduced at the coordinator seam: push f9=90s, then `runCycle(0.2, newer)` resets it to f1=5s). Fix: `onReaderClosed` now captures the narrating fragment and, on the flush scope, re-pushes `pushAudiobookFromReadingPosition(fragment)` LAST (after the reconcile, same coroutine → always wins). **DEVICE-VERIFIED 2026-06-12** on Riffle_RA_Repro (split-library Martian: ebook 551dfeec + audiobook 977c32b7, both confirmed-matched to Storyteller bundle 1385738337074647): did a real Play-From-Here (selection→action-mode "PLAY FROM HERE" via long-press-drag at DevTools-derived coords), left the reader, opened the audiobook player → it resumed at the narrated sentence (`startAtSec=4013.08`, open-reconcile `jumpToAudioSec=null`), NOT the chapter start. The clobber + correction is visible in the `onReaderClosed` log: reconcile `PATCH audio currentTime=3991` then my re-push `PATCH audio currentTime=4013`. So if the user still sees the bug, suspect a STALE BUILD first. **SECOND, distinct bug (the one the user actually hit — onReaderClosed fix did NOT cover it; device-verified by direct ABS injection 2026-06-12):** the AUDIOBOOK PLAYER's open-reconcile (`AudiobookPlayerViewModel.attachReaderSync` → `runAudioLedCycle(curSec, localUpdatedAt=0L)`) is inbound-only last-update-wins. When the EBOOK reading-position peer is NEWER than the AUDIO peer (it gets bumped fresh by readaloud auto-follow during a "play from here" session) AND behind, the cycle returns a BACKWARD `jumpToAudioSec` and the player SEEKS BACK to where the *reader* sat = "audiobook plays from the beginning of the chapter". Reproduced deterministically: PATCH audio=8465s, ebook=ch4-top(3647s) with a newer stamp → open → `jumpToAudioSec=3647.08`, player jumped to 1:00:47. FIX: `audiobookForwardInboundJump(jumpToSec, resumeSec, eps)` — honour an inbound jump only when FORWARD (> resume + SETTLE_EPS_SEC); a backward jump is the reading-position peer dragging the listen back. Applied at attachReaderSync AND the follow-loop inbound branch. Verified: same injection → player resumes at 2:21:10 (8470s), not chapter 4. Unit test `AudiobookForwardInboundJumpTest`. NOTE: the cycle's OUTBOUND still briefly writes the audio peer to the ebook winner (3647) on open, but the auto-play follow-loop + pause/close push the correct forward position within ~10s, so it's transient (only an open→process-death-within-10s edge loses it). This is an ADR-0029 reconcile-semantics nuance: forward-only suppresses a *deliberate cross-device backward* ebook move too (rare). Deterministic repro trick (no flaky UI selection): login test/test → curl PATCH /api/me/progress/{ebookItem} and /{audiobookItem} directly to set positions+timestamps, then open the player. WebView "Play from here" CAN be driven: long-press-DRAG (start mid-screen, not near the page-turn edges) raises the action-mode toolbar; tap PLAY FROM HERE (find coords by screenshot, a11y tree doesn't show the floating toolbar).

KNOWN remaining edge (NOT device-verified, reasoned only): pressing X (closeReadaloud) *then* leaving may still clobber — `_readaloudOpen` is false so narratingFragment is null; closeReadaloud's push updates the reading-position localUpdatedAt to its own server stamp, so the leave-reconcile sees local=audio tie → local wins → writes reading position to audio. Proper fix would track a session `lastNarratedFragment` (or stop the reconcile regressing the audio below the last precise push). Instrumentation used: tag `RIFFLE_ABSYNC` (println in pure-JVM core:network AbsApiClient, android.util.Log in app VMs) — stripped after diagnosis.
