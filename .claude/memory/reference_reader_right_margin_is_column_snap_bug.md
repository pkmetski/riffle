Symptom: reflowable EPUB page shows a left margin but text flush to the right edge (worse with justify). NOT the EPUB and NOT a ReadiumCSS body-padding/`box-decoration-break` issue.

TRUE root cause (measured live via WebView DevTools, book "Influence without authority" e0bfbef0…, on Medium_Phone API-25, dpr 2.625):
Readium's reflowable paging snaps scrollLeft to multiples of `b = Android.getViewportWidth()/devicePixelRatio` (see `function O(u){var t=u+1;return t-t%b}` in readium-reflowable.js; restore=`scrollToPosition`→`O(scrollWidth*frac)`, page-turns→`O`). But the CSS column pitch is `window.innerWidth`. With non-integer dpr these differ: 1080/2.625 = **411.43** vs innerWidth **412** → 0.57px/page error that ACCUMULATES. Deep in a chapter (e.g. page 33: scrollLeft 13576 = 33×411.43, but column boundary = 33×412 = 13596) the page sits ~20px off the column grid → leading margin grows, trailing margin → 0. Snapping scrollLeft to the nearest multiple of innerWidth restores symmetric 20/20 (verified live: 40/0 → 20/20).

Option 1 (post-hoc re-snap) TRIED AND REVERTED — it works (margins corrected, verified end-to-end) BUT causes a visible page JUMP on every page-turn: Readium animates the turn to its own off-grid position and PAINTS it there, then the snap moves scrollLeft to the column grid ~one beat later → a visible hop that grows with chapter depth (the accumulated drift). No timing/debounce tweak removes it — any after-the-fact scroll correction is intrinsically a visible jump. User rejected it. Fully reverted (no PAGINATION_SNAP_JS / snapToColumnGrid / PaginationSnapJsTest in tree).

Only JUMP-FREE fix = option 2 (native): make Readium land on the column grid in the first place by sizing the reader so `getViewportWidth()/dpr` is an integer == innerWidth (== column pitch). Concretely, constrain the reader AndroidView width to the largest dp value C where C*density is an integer (dpr 2.625 → C=408dp → physical 1071 → b=innerWidth=408), centered. Cost: a tiny symmetric gutter (~1.7 CSS px/side at dpr 2.625 — negligible).

IMPLEMENTED (branch `pkmetski/reader-right-border-fix`, EpubReaderScreen.kt): pure `internal fun alignedReaderWidthDp(availDp, density)` + a `BoxWithConstraints`/`readerModifier` that constrains the reader AndroidView width ONLY in single-page paginated mode (`alignViewport = isPaginated && !isDoublePage`); scroll/fixed/double-page keep `Modifier.fillMaxSize()` (byte-identical to before). Gutter painted with `formattingPrefs.theme.palette.background` so it's invisible. Unit test `AlignedReaderWidthTest` (6 tests). Verified on-device (Medium-Phone API-25): paginated → androidVW 1071, innerWidth=b=408, deep pages 0px off-grid L20/R20, real swipe 7752→8160 lands on-grid with NO jump; scroll mode full-width/unaffected. Did NOT need per-mode gating beyond paginated. ScrollBoundaryNavigationContainer logic untouched.

Why other paths are out: option 3 (newer Readium) dead — 3.3.0 has identical `b` derivation + the highlight regression. Option 2's JS form (override getViewportWidth) infeasible — read-only @JavascriptInterface (reassignment silently no-ops, verified live).

REVISION (branch `pkmetski/book-margins-physical-device`, 2026-06-07): the exact-integer-b alignment had a device-dependent flaw — it produced LARGE symmetric margins on physical devices in paginated mode only (book e0bfbef0…). Cause: `density = densityDpi/160`, so its lowest-terms denominator divides 160. Standard phone BUCKETS (2.625=21/8, 2.75=11/4, integers) → whole-pixel widths a few dp apart → tiny gutter (why it never showed on the emulator, always a clean bucket). But a densityDpi **coprime to 160** — common on real hardware and especially after the user changes "Display size" in system settings — spaces whole-pixel widths up to 160dp apart, so insisting on an exact one shaved 100+dp off the page (e.g. dpi 411→2.56875 gave a ~100dp gutter). Proven numerically: dpi 393/401/411/377 → 100–138dp gutters vs ~3dp on the 420 bucket. FIX: `alignedReaderWidthDp` now caps the sacrifice at `GUTTER_BUDGET_DP=8` and, within that budget, picks the width with the smallest snap error frac(width*density) — an exact whole-pixel width when one's in range (zero drift, byte-identical to before on every real bucket + integer density), else the closest partial alignment. Residual error is sub-pixel/page, imperceptible over a chapter (~5px/40pg worst case) vs the ~20px the alignment exists to kill. Regression tests added (`bounds the gutter on a density coprime to 160`, `gutter never exceeds the budget for any density` over dpi 120–640). The fundamental tradeoff: you CANNOT have both exact-integer b (zero drift) AND a small gutter on a coprime densityDpi — they're mutually exclusive — so the budget cap deliberately trades a sliver of drift for bounded margins on all devices.
