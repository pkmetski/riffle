Reader-navigation bug (branch `pkmetski/reader-navigation-broken`): tapping an in-document cross-reference like "Figure 4.1" (`<a href="#c04-fig-0001">`) left the reflowable page stuck split between two columns. Root cause: `FootnoteAnchorBridge`'s JS click listener calls native `onAnchorTap(id)`; for non-footnote targets the handler returned **false** → no `preventDefault` → the **WebView's default same-document anchor scroll** ran, which sets `scrollLeft` to the element's raw offset (mid-column in a paginated column layout), with no re-snap. Footnotes worked because they returned true (popup). Verified live on book e0bfbef0 / c04.xhtml, dpr 2.625: browser default landed scrollLeft≈932 (page_b 2.27) → figure cut off on the right.

Fix: added `FootnoteResolver.classifyAnchorTap` → `AnchorTarget.{Footnote,CrossReference,Unresolved}`. The bridge handler navigates CrossReference targets and returns true to `preventDefault`. Unresolved (cache cold / id absent in the *visible* resource) still defers to the WebView. Note the handler keys off `currentHrefHolder[0]` (the visible resource) — fine for real taps since you can only tap an on-screen link, but means a CDP `el.click()` on an offscreen pre-rendered page classifies Unresolved.

SNAPPING IS NOT SOLVED — branch is on **Readium 3.3.0** (main merged bump #86; the 3.0.0 pin lives only on the readaloud-api25 branch). On 3.3.0 + dpr 2.625, tested ALL three nav strategies live (on-device logs + before/after screenshots):
- `go(cssSelector "#id")`: RELIABLY brings the target into view but lands flush to the element's box → ~one-gutter (~28px) off the column grid (right-edge sliver). Same drift that makes TOC/search `go(link)` land "slightly shifted" (issue the user reported).
- `go(progression)`: imprecise on 3.3.0 — landed me on the figure once (1645) but the user saw it jump to chapter start. Don't trust it.
- `goForward`/`goBackward`: **return `true` but DON'T move the page** on 3.3.0 (confirmed: log says result=true, before/after screenshots identical). So page-flip snapping is impossible here. (May differ on 3.0.0 — untested.)
- `fragment.evaluateJavascript(...)`'s RETURN value is also unreliable on this WebView (the JS executes but the result comes back null/empty), so don't compute values in JS and read them back via the return — push them through a @JavascriptInterface bridge call instead.

CURRENT STATE (in tree, not committed) — TWO-PART FIX:
1. **Native viewport-resize (VERIFIED live)**: in `EpubNavigatorView`, constrain the reader AndroidView to `readerWidthDp.dp` where readerWidthDp = largest dp ≤ screenWidthDp whose physical px (`dp*density`) is an exact integer; centered, `fillMaxHeight`, parent Box background = `formattingPrefs.theme.palette.background` (gutter colour). On dpr/density 2.625 this is 408dp (1071px) → innerWidth becomes **408 == snap pitch**. VERIFIED: after a CLEAN install, CDP showed innerWidth=408 and normal pages land at exact multiples of 408 (mod=0) — the accumulating drift is GONE, so TOC/search/normal-page navigation all snap. This also fixes [[reference_reader_right_margin_is_column_snap_bug]]. (Self-disables on integer-density devices: readerWidthDp == full width.) GOTCHA: an `install -r` over an old build did NOT pick up the new innerWidth — needed `adb uninstall` + fresh install (then re-add server). Verify innerWidth via CDP, don't assume.
REBASE/CANONICAL STATE (as of branch pkmetski/reader-navigation-broken rebased onto main): the viewport-resize shipped as PR #95 — `alignedReaderWidthDp(availDp,density): Float` in `ReaderViewportAlignment.kt`, gated to single-page paginated mode (`alignViewport = isPaginated && !isDoublePage`) via `BoxWithConstraints`+`readerModifier` in EpubNavigatorView. Reader JS lives in `ReaderWebViewScripts.kt` (RECT_TO_JSON_POLYFILL_JS, SELECTION_SPAN_TRACKER_JS, autoFollowSnapJs, firstVisibleSentenceJs, and — added for this fix — `scrollToColumnJs(id)` + `SNAP_NEAREST_COLUMN_JS`). My earlier `ColumnSnap.kt` was the pre-rebase duplicate; deleted (snappedWidthDp == alignedReaderWidthDp). A `git stash pop` of pre-rebase work conflicted in the viewport region — resolve toward the committed `alignedReaderWidthDp`/`readerModifier` side.

GOTCHA that caused "TOC navigates close to a chapter but not exactly": do NOT run the column-snap in `paginationListener.onPageLoaded` — the typography injection there reflows the page asynchronously, so a snap at that point rounds a PRE-reflow position. Snap only in the nav handlers AFTER `go()` (suspend) returns; for a cross-resource jump `delay(NAV_COVER_SETTLE_MS=100ms)` first so the reflow settles, then snap. The `navigating` cover masks that whole window.

IMPORTANT: the resize fixes DRIFT (normal page-turns via Readium's O() snap) but does NOT fix go()-to-a-fragment, which lands flush to the target element (a gutter into its column) → leading text clipped. So TOC/search/figure navigation each still need an explicit column-snap on top of the resize. The user confirmed TOC nav was still off-grid after the resize alone.

SNAP LOGIC EXTRACTED to `ColumnSnap` (internal object, unit-tested in `ColumnSnapTest`): `snappedWidthDp(maxWidthDp,density)` (the width calc), `scrollToColumnJs(id)` (floor to element's column — figure links), `SNAP_NEAREST_COLUMN_JS` (round to nearest column — TOC/search). Width calc is pure/testable; JS snippets tested by content assertions.

JUMP CAVEAT: snapping AFTER `go()` returns causes a visible hop ~0.5s post-nav (off-grid paints, then snap corrects — the intrinsic post-hoc-snap jump). Fix attempt: ALSO snap in `paginationListener.onPageLoaded` (fires when the page is rendered → correction coincides with paint, no visible hop) while keeping the post-go snaps as a safety net for same-resource navs where onPageLoaded may not fire. Unverified on-device.

TOC also enters immersive: `onEntryClick` in EpubReaderScreen calls `viewModel.navigateToEntry(entry)` then `immersiveState.hide()` (hide() = enter immersive).

2. **Column-snap after go() (implemented, NOT finally confirmed on-device)**: figure cross-reference taps run `ColumnSnap.scrollToColumnJs`; TOC/search/server-locator handlers run `ColumnSnap.SNAP_NEAREST_COLUMN_JS` right after the suspend `go()` returns, plus onPageLoaded — sets `scrollLeft = floor((elemLeft+scrollLeft)/innerWidth)*innerWidth`, i.e. the figure's column boundary. Replaces go(cssSelector) which landed flush-to-element (~29px into the column → sliver). Argued safe: on the resized clean grid the snap target IS a Readium page boundary, so even if Readium re-asserts it lands on the same spot (unlike the pre-resize post-hoc snap that fought Readium's 411.43 grid). Couldn't get a final live confirmation — the emulators on this Mac were being killed every ~1-2 min by something external (watchdog/memory), and a cold AVD boot wiped the Riffle install. ASK THE USER to confirm the figure link on their device; if it doesn't hold, fall back to go(cssSelector) (verified to reach the figure with the sliver).

3. **Cross-chapter load-flash cover (NOT confirmed on-device)**: user saw "a graph flashing almost every time" on TOC nav. Cause: a cross-resource go() makes Readium briefly paint the new chapter's opener graphic / a white blank before scrolling to the target (and the post-go snap nudges a beat later). Fix in EpubNavigatorView: a `navigating` page-coloured cover Box (drawn last in the reader Box, `formattingPrefs.theme.palette.background`) shown ONLY for cross-resource jumps (compare `link.href.substringBefore('#')` vs `currentHrefHolder[0]`), held through go()+snap + `NAV_COVER_SETTLE_MS`(100ms) so the snapped page paints underneath before reveal, reset in `finally`. Same-chapter jumps aren't covered. Server-locator (peer/resume sync) snaps but is never covered (would flash mid-reading). `ColumnSnapTest` covers snappedWidthDp + the two JS snippets.
