Bug family (branch pkmetski/fully-read-position-stale-progress): after mark-as-read → open → navigate past cover → exit, the book stayed at **100%** (both library + detail bars) and stayed in Completed, though the reader position was saved correctly. Reopen-from-beginning was a *separate* issue already fixed by dropping the old `resumePositionFor(saved, readingProgress)` helper for a plain `positionStore.load(...)` (finished books now resume where left off).

**TWO root causes, both needed:**

1. **Local write on a cancellable scope (primary).** In the reader `onReaderClosed`, the *position* save was moved to the survivable `ProgressFlushScope`/`ApplicationScope.launchSurvivable` (ADR 0036), but the **`readingProgress` fraction write** (`positionSaveCoordinator.onClose(...)`) still ran on `viewModelScope.launch`. Back-navigation calls `onCleared()` immediately → cancels `viewModelScope` **before** that coroutine runs → position lands, fraction does not → `readingProgress` stays 1.0. It's a **race**: hit deep chapters sometimes, missed others. Fix = run the `onClose` fraction write inside the same survivable flush block as the position save. Files: `EpubReaderViewModel.onReaderClosed`, `PdfReaderViewModel.onReaderClosed` (both Android/app), and shared `CbzReaderViewModel.onReaderClosed` (was in `savePosition`'s viewModelScope.launch). iOS `IosEpubReaderScreen`/`IosPdfReaderScreen` were already correct (`CoroutineScope(SupervisorJob()).launch` in onDispose).

2. **ABS sticky finished-state — NOT actually needed (tried `readingPushFinishedFlag`, then DROPPED).** ABS keeps `isFinished`/`finishedAt`/`progress=1` sticky; a bare `ebookProgress` PATCH doesn't clear them. I first added `readingPushFinishedFlag(fraction)` (push `isFinished=false` on sub-1.0 reads) to clear the server flag. But it's **redundant**: the app already ignores ABS's sticky flag — every pull *derives* finished from `ebookProgress >= 1` (`toCatalogProgress`/`pullAllProgress`, commit 0caa388d2). Deterministically verified on-device: set ABS `ebookProgress=0.45, isFinished=true` → app held `readingProgress=0.45, finishedAt=null`, no re-stick. So once fix #1 keeps the local DB correct, the sticky flag is inert. `readingPushFinishedFlag` was reverted at the user's request to shrink the diff. The re-stick I saw early on was fix #1's race (DB stuck at 1.0 → sweep pushed 1.0), not the server flag.

Library In-Progress vs Completed is driven purely by `readingProgress` (`>0 && <0.99` vs `>=0.99`); `finishedAt` only orders the Completed shelf, so a lingering `finishedAt` is cosmetic and the per-item pull clears it (`refreshItemProgress`: `if (!sp.isFinished) updateFinishedAt(null)`).

Verified on AVD 5554 with a pristine book via pure UI: mark-read → open → jump to ch8 → exit → detail shows 25%, In Progress; reopen resumes at ch8; stable across relaunch.

**Follow-up bug (same branch): library bar ≠ detail bar for the same book.** Both read `library_items.readingProgress` via the same Room flows, so a persistent mismatch means the stored value oscillates. Smoking gun (confirmed against the live ABS server): ABS's **bulk `/api/me` endpoint lags its per-item `/api/me/progress/:id` endpoint** (eventual consistency) — at one instant per-item returned 0.55 while bulk returned 0.34. The **detail** re-pulls per-item on every open (fresh); the **library** only updates on the bulk sweep (lagging) — so they fight, writing different values to the one row. Fix = **last-update-wins**: new `library_items.progressServerUpdatedAt` column (Room MIGRATION_74_75, iOS schema v5→v6) holds the ABS `lastUpdate` of the stored fraction; new DAO `updateReadingProgressFromServer(...)` writes only when `serverUpdatedAt >= progressServerUpdatedAt`, so a lagging bulk pull can't overwrite a fresher per-item value. Server pulls (`refreshItemProgress`, `refreshLibraryItems` bulk loop — Android + iOS `IosLibraryRefresherImpl`, sweep `LibraryItemUiProgressSink` via `UiProgressSink.apply(..., serverUpdatedAt)`) use it; local reader-close / mark writes use `updateReadingProgressStamped(clock.nowMs())` so they always win. iOS library-list DTO needed `AbsProgressDto.lastUpdate` + `NetworkLibraryItem.progressUpdatedAt` plumbed through. Verified on-device deterministically: local stamp far-future + lower server value → server pull rejected, bar held.
Debug method that finally worked: temporary `logger.d(LogChannel.ProgressSync)` "WRITE[bulk/per-item/mutator]" logs at every readingProgress writer + `grep RIFFLE_PS`, plus curl-comparing the two ABS endpoints at the same instant.

**Debugging traps (cost hours):** don't over-manipulate one test item — injecting fake audio via ABS PATCH creates an `audiobook_positions` row that activates the audio reconciler (`fraction=1f` when finished) and confounds everything. `run-as sqlite3` CLI writes vs the app's Room **WAL** conflict (my reset to 0.28 got overwritten by uncheckpointed app frames) — always force-stop the app AND `PRAGMA wal_checkpoint(TRUNCATE)` before trusting a CLI read/write. Verify via **UI screenshots** (what Room actually committed), not CLI reads while the app runs.
